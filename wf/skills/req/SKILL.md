# ① 需求确认

**前置**：`design.md`「零、背景资料」没有内容 → 先走 `/wf:research`，别空手开始问需求。
**输入**：用户口述 + 「零、背景资料」→ **产出**：`design.md` 第一章
**验收**：1.1 目标 / 1.2 功能边界 / 1.3 接口约定 / 1.4 验收标准 四小节全部填完，无 TODO。

## 讨论风格：教学模式

**一轮只给一小块，结尾抛一个开放问句，等用户先想。** 不要一次性把话讲完——那是讲义，不是讨论。用户想岔了我再纠；用户想对了直接往下走，不复述他刚说的。

这条覆盖本阶段全部输出：**结尾是问句，不是总结**。

## 怎么问

按 `RULES.md` 三层提问走，本阶段主要在**第一层（要什么效果）**：目标是什么？边界到哪？做成什么样算完成？

**先问用户有没有自己的方向**，再分两条路：
- **用户有方向** → 针对这个方向评价、挑问题，不绕开它另起一套。
- **用户没方向** → **先引导，不给答案**。见下。

## 用户说「不知道」时怎么引导

⛔ **禁止直接铺流程清单。** 用户说「不知道电机怎么写」，回「先通信、再读值、再 PID」＝把他要自己走的路铺完了，他学不到东西。

1. **找锚点**：从他已经会的、见过的东西起问，不从领域知识树的根起。
2. **问机制，不问名词**：「电机是怎么被控制的？」✅ ／「你知道 PID 吗？」❌ ——要他描述因果和现象，不是背术语。
3. **一次一问，等他答。** 答不上 → 把问题再拆小一层，**仍然不给答案**。
4. 拆到最小还答不出 → 只给**一个**最小提示（一个概念 / 一句话），立刻把问题抛回去。
5. 他推出来了 → 直接往下走，不复述他刚说的，不补一遍"完整版"。

引导到他能说出方向为止，再回到上面「用户有方向」那条走。真的引导不动（缺的是硬知识不是思路）→ 才摆选项讲代价，摆完主动反驳自己一遍。

**答案必须用户亲口说出来**。

⚠️ 反驳只挑真正影响目标/验收标准的代价，不为了显得全面硬凑理由——那样会把简单需求问出不必要的复杂度。

## 禁止

- 禁止替用户补全需求，禁止「我理解为…，对吗？」这种只需点头的问法。
- 只写 / 改 `design.md` **第一章**，禁止碰第二章。
- 需求不清就停下问，不许先写代码「以后再改」。

## 收尾

第一章填完 → 走 `/wf:wrap`，下一阶段 `/wf:design`，`建议档位：高`。
