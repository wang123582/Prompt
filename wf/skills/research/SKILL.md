# ⓪ 资料收集

**触发**：任何新项目（`/wf:intake` 分诊为①）、或老项目要接一个新功能，进 `/wf:req` 之前都先走这一步。
**输入**：用户口述的方向 + 项目现状 → **产出**：`design.md` 新增「零、背景资料」一节
**验收**：「零」前两条是 `直觉：` 和 `真样本：`；内部、外部都至少过一遍，每条资料标来源，没有编造的内容。

## 先直觉 + 真样本，后资料

本阶段负责 `RULES.md`「工作顺序」的**直觉**层：先回答「这东西大概长啥样」，再去查「它到底怎么成立」。
- 找一个现成的同类东西（开源项目、官方 example、最小 demo），能跑就跑一下，跑不了就看它的 README / 目录结构。
- 写成一屏以内的 `直觉：<类比或一张小表 + 来源>`，放「零」第一条——它是 ①req 立问题、②design 画链路图的起点。
- **拿一条真样本**写进 `真样本：`：真输入 + 期望输出（太大就写形状 + 一个片段）。用户手里有就要过来，没有就从同类项目 / 官方数据里找并标来源；都没有写「未找到，需用户提供」，**不许编一条充数**——后面的链路图、测试都拿它走。
- 资料只查到**选型和接口级**；具体 API 用法、参数细节留给 ④exec 用到时再查，不在这里全量啃。
- 出口：用户拿着样本说得出「进去是这样，出来是那样」。说不出来就还没完，不进 ①req。

## 查什么

1. **内部**：代码根 `CONTEXT.md` 索引到的相关模块、`design.md` 里同领域已有的现状记录、`tasks/progress.md` 有没有做过类似的事——别重复造轮子，也别和已有设计打架。
2. **外部**：这次要用的库 / 框架 / 协议的官方文档、版本变更、已知坑；有明确外部系统（下位机协议、第三方 API、SDK）时优先查一手资料，不凭印象臆造接口。

## 怎么写

- 只写 / 追加 `design.md`「零、背景资料」，不碰其它章节（同 `PROMPT.md`「章节互不删」约定）。
- 每条资料带来源（文件路径 / URL / 命令输出），没有来源的判断标「推测，未核实」。
- 查不到就写「未找到，需用户提供」，禁止编造资料充数——这是需求阶段最容易埋雷的地方，宁可留空等用户补，不许拿猜的当结论喂给下一阶段。
- 资料量按需，不为了查而查；已经明确到不需要查的部分（用户已经把接口 / 需求讲死）可以跳过，别做无意义调研拖慢节奏。

## 收尾

写完 → 走 `/wf:wrap`，下一阶段 `/wf:req`，`建议档位：中`。
