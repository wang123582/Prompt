# ⑤ Review

**输入**：已实现的代码 → **产出**：审查结论 + 修复

## 审前：合上讲一遍

不看代码，先用三句话讲这个模块：**解决了什么问题 / 核心思路 / 局限在哪**（`RULES.md`「工作顺序」的**合上讲**层）。
- 第一句对照 `design.md` 1.1 `❓要解决的问题`，对不上就是头号问题。
- **讲不出来、或讲出来和 `design.md` 第二章对不上的那句，就是先审的地方**——审查从那里开始，不平铺全量过。
- 局限那句写不出来 = 还没审透，不许收尾。讲出来的局限对照 1.2「已知局限」和各模块「局限」，文档里没有的列进审查结论。

## 审什么（按顺序）

1. **对不对**：逻辑是否符合 `design.md` 第二章；边界条件（链路图上标的空 / 缺 / 脏 / 超范围数据）、错误路径有没有按图处理。
2. **测得住吗**：pytest 是否真覆盖核心分支，还是只测了 happy path。
3. **耦合**：有没有偷偷跨模块直接调用，破坏阶段② 定下的解耦。
4. **多余物**：调试残留、失效代码、重复实现（判定标准同 `/wf:wrap` 第 1 步）。

## 规矩

- 发现问题**先列清单 + 判定依据**，再动手改。
- 只改本次审查范围内的代码，不顺手重构无关部分。
- 改完重跑 `pytest` / `mypy` / `ruff check` 并贴输出。

## 收尾

→ 走 `/wf:wrap`。
